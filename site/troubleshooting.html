Troubleshooting

Almost every "problem" with Brain Stem is actually a safety guard doing its job on purpose. This page lists the moments that feel like failures — a refusal, an exit code, a file that appeared somewhere unexpected — says plainly what each one means, and gives the next step. Every row traces to a real, documented behavior; nothing here is guesswork.

Ordered the way a first-time adopter meets them: installing, onboarding, upgrading, then everyday use. Each row links to the page that explains the behavior in full.

Installing

You seeWhat it meansDo this
You ran bash install.sh and… nothing was installed. That is the design, not a failure. The bare command is a dry run: it prints an action plan of everything it would do and writes zero files. Read the plan, then re-run the same command with --apply (and CLAUDE_HOME set). → Install guide: Step 1
The installer stops with exit code 10. --apply ran without CLAUDE_HOME set. Real writes refuse to guess their destination; a preview may assume a target, an apply may not. export CLAUDE_HOME=~/.claude, then re-run. → Packaging: dry-run, then --apply
The installer refuses because ~/.claude already contains files it did not put there (or you see exit code 51 at apply). The foreign-content guard: it will not overwrite an existing Claude setup without your explicit acknowledgement. The dry run lists everything it needs under required_overrides. Add the flags it names — typically --force-install --i-understand-overwrite-risk --backup-dir <path>. → Install guide: installing over existing files
It refuses because jq (or python3, plutil, sqlite3, shasum) is missing. The helper-programs gate: the installer hard-requires a few standard tools and stops rather than limping. Install the missing tool (brew install jq for jq) and re-run. → Install guide: before you begin
It refuses because you are running as root / with sudo. The blast-radius guard: a personal install never runs as the all-powerful account. There is no override, by design. Run as your normal user account. → Packaging: pre-flight gates

Onboarding

You seeWhat it meansDo this
/onboard prints "Onboarding already complete — nothing to do." Setup finished earlier and recorded its marker; a plain re-run protects your personalized files by doing nothing. Nothing is wrong. Use /onboard --force only if you truly mean to redo setup. → Onboarding: run once
A one-line banner keeps inviting you to finish setup at the start of each session. Onboarding was started but never completed. The nudge is advisory — it never blocks you. Run /onboard --resume to pick up where you left off. The banner disappears for good once setup completes. → Onboarding: the reminder
Onboarding wrote a file ending in .new instead of replacing your existing one. Block-and-log protection: your existing file differs from what would be generated, so the new version is set aside and your file left untouched. Review the differences it shows you; replacing the file is opt-in via --force. → Onboarding: safe re-run
It refused to write a file because template blanks ({{…}}) were left in it. The leftover-blank guard: a half-filled instructions file would literally say {{IDENTITY_NAME}} to the assistant, so the write is refused. Re-run — onboarding re-fills and re-checks. You should never see this twice. → Onboarding: what it produces

Upgrading

You seeWhat it meansDo this
git pull in your clone reports "divergent branches" or a "(forced update)". The published history was realigned at some point; your older clone cannot fast-forward. git fetch origin && git reset --hard origin/main — or delete the folder and clone again. This touches only the clone, never your install or vault. → Install guide: upgrading
The upgrade stops with exit code 56 — "delivery shortfall". The delivery gate: some managed file did not reach the new version, so the upgrade refuses to record itself as finished. Nothing is in a broken state. Run bash install.sh --upgrade --apply again — it resumes and converges. → Packaging: the delivery gate
After an upgrade, a migration id is missing from the version stamp's applied list. Even a past upgrade that advanced the stamp without running a migration is healable — the runner selects anything not yet recorded. Check with jq -r '.migrations_applied[]' "$CLAUDE_HOME/governance/.installed-state.json"; re-run the upgrade apply once — it picks up the missing migration. → Install guide: the post-apply self-check
The upgrade suddenly demands CLAUDE_HOME, a backup directory, and override flags it never asked for before. The one-command lane verifies your install's version stamp first; if the stamp is absent, unreadable, or its fingerprint does not match, it fails closed into the full ceremony rather than guess. Provide what it asks for — this is the installer declining to upgrade a folder it cannot prove is its own install. → Install guide: upgrading in place
A file you edited now has a twin ending in .foundation-local. Not a failure: the upgrade delivered the new version and preserved your edited copy alongside it instead of overwriting it. Keep your edit, adopt the new version, or carry your change into the overlay — the divergence is also visible to the census. → Packaging: two reasons a file can differ

Everyday use

You seeWhat it meansDo this
An in-flight message says you are editing a managed surface. The write advisory: the file you touched is on the install receipt, and hand-edits silently fork your install from the product. The write still proceeds — the advisory teaches. Prefer the sanctioned routes: change it upstream and upgrade, or express the difference through the overlay. MANAGED_SURFACE_OK=1 acknowledges a deliberate temporary exception. → Packaging: managed surfaces · → Configuration
A census or full librarian pass reports a managed-surface-fork. A shipped file's bytes no longer match its recorded fingerprint — an edit, an outside tool, or a scheduled job changed it. The census detects; it never auto-fixes. Same sanctioned routes as above; known forks are not re-reported every run. → Packaging: the census
You went looking for session checkpoints, scratch files, or lock files inside ~/.claude and they are not there. Runtime state deliberately lives outside the program folder, split by how much you would care if it vanished: durable data under ~/.local/share/brain-stem/, throwaway state under ~/.local/state/brain-stem/. Nothing to fix — that is the two-root split. → Packaging: where runtime state lives
bash uninstall.sh refuses — no install log. The provenance check: the uninstaller double-checks it is pointed at a folder Brain Stem genuinely installed, and refuses otherwise. Run it against the install home with CLAUDE_HOME set. → Packaging: uninstall
After uninstalling, settings.json / settings.local.json are gone. The one named exception: those two files are not fingerprint-tracked, so they are removed by name. Your copies survive in the timestamped pre-uninstall backup. Take your versions back out of the .pre-uninstall-<timestamp>/ backup. → Uninstalling
