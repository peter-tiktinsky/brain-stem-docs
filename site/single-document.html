System governance · the single-document pillars

The Single Document

The first family of governance rules governs one file on its own — how it's identified and labeled (frontmatter, tags, name) and how its body is structured (the type contract). This page takes each of the four pillars in turn: the gap it fills in native Claude Code, the reasoning behind its shape, and exactly how it operates at the moment of a write.

The narrative companion to the foundation's frontmatter, tagging, naming, and file-type-contract rules. Every rule here is checked at write time against one merged contract.

One contract, composed from two files — read on every write

Each rule below is read the same way. At every write the assistant makes with its Edit and Write tools — a file put on disk by a shell command is not checked — the engine merges foundation-master.json (the defaults every adopter receives) with overlay-master.json (your extensions, empty on a fresh install) and applies the union as the live contract. Foundation provides the baseline; your overlay extends the type registry, adds tag dimensions, declares new folders, and shadows a shipped default only where you've registered a stated _override_reason. The shape of that merge — sealed base, transparent overlay, overlay-wins with a stated reason — is itself the pattern Kustomize, git config, and the CSS cascade arrived at independently. See the governance engine.

Frontmatter — what a file declares

The gap in native Claude Code

Claude Code auto-loads a CLAUDE.md and reads any file you point it at — but to the platform every file is undifferentiated text. Nothing declares what a file is, what fields it must carry, or where it belongs; there is no write-time schema and no required-field check. So the structured handles that routing, auditing, and capture pipelines depend on simply don't exist until something supplies them. Frontmatter is that something.

Frontmatter is the YAML block at the top of every vault file, and the system reads it on every write to decide whether the file is well-formed and where it belongs. Fields like type, tags, and updated are not decoration — they are the structured surface the system reads (tags, covered next, are the surface you query). The payoff is that a file is legible to the machine the moment it lands, instead of being an opaque blob a later pass has to re-interpret.

The three compliance tiers

Every file type carries a tier — assigned per-type, not per-file — that decides what happens when a write fails its contract. This is the load-bearing idea: enforcement strength is matched to who authored the file.

TierOn failureDefault class of files
StrictWrite is denied; the missing fields are named.System-emitted files — scaffold output, captured content, scraper output, anything written by a skill without a human in the loop.
StandardWrite proceeds; an advisory surfaces at session close.User-authored content — your own notes, references, planning docs.
MinimalDeclared in the registry as allow-through.No shipped type carries it — the split that fires at the write is Strict versus Standard.

Foundation types are all Strict because they're machine-emitted; the user-authored types you register typically run at Standard. The tiering is why the system can be uncompromising about generated files — which a human never sees and which downstream tools depend on — while staying gentle about the note you're actively writing. Blocking a person's save over a missing field would be hostile and would only train you to switch the guard off.

The identity cohort — and how a note comes to carry it

Beyond the per-type baseline, the registry declares a small identity cohort that the user-facing content types share: description (a one-line summary, at most 200 characters), created, id (a stable slug derived from the file's path) and schema_version. Which types require it is declared per type, not assumed: the index, reference, deliverable and note types carry the full set; a log, a writer record or an ideation brief does not; plan artifacts and memory files run their own registries with their own required sets. The cohort's job is identity and orientation — for you, for Claude, and for any outside reader (Knowledge-graph extendability).

You almost never fill it in by hand. Three mechanisms cooperate:

  • Stamped at creation. A note written through Claude Code inside the vault is stamped by the post-write hook with whichever of the four fields it lacks: created is derived (an in-band modified date, else the file's first git commit date, else today, labelled as a bootstrap date) and never re-stamped once present; id is a slug of the path; schema_version is the current integer; description is drafted from the first heading or opening line, with no model call (a model-drafted description exists as an opt-in switch and is off by default). Memory files, folder indexes and logs are excluded; they have their own writers.
  • Backfilled on demand. For notes that already exist, the librarian's frontmatter capability proposes the same four fields for any file missing them, using the first git commit date or the file's birth date for created. Its check mode reports; its fix mode writes; you can pass --frontmatter-fix to an upgrade to run the backfill once the new files land. Run it in check mode first and read the findings before you let it write.
  • Warned, not blocked. A missing cohort field surfaces as an advisory on every tier, including Strict, because the first two mechanisms make the note compliant on their own. The value formats are checked the same way (a date must look like a date, tags must be a list, id a slug, schema_version an integer) and the check is advisory too. What a Strict type still denies is a missing field outside the cohort — a deliverable without its project, status and audience, for example.

Scope is decided by location, not by a list of names: the check applies to Markdown written under the vault root, and a registered work project's files are mapped onto the vault view before the check so they are governed too. Files the system parks outside the vault — logs, runtime state — are out of scope because of where they live.

The foundation type registry

Foundation ships a type only when it has a foundation consumer — a hook, a skill, a mandate, or a contract. Everything else is left to your overlay so you shape your own vocabulary. The content types share a baseline of type, tags, updated; the operational log and the plan-tree ideation-brief carry their own minimal sets.

The registry is deliberately small — only types with a consumer. To validate a recurring document the foundation doesn't ship a type for, run /govern register --kind file-type; it writes the new type into your overlay under frontmatter.types with its required fields. To raise or shadow a foundation default, register the same type with an _override_reason — the system denies an override that lacks a stated reason, so every divergence carries its rationale. (Plan-tree files like spec.md and manifest.json are governed by the plans pillar, not this registry; see Plans.)

The folder-lineage convention

Folders don't carry frontmatter, so any lineage that lives at folder level — which cluster is this file part of — has to propagate down into the file. The convention: a file inside a structural cluster folder carries both the matching frontmatter field and the matching tag. Foundation ships the shape of these rules; your overlay's path_routing rules (declared at onboarding) define the cluster grammar — the path glob, the required lineage fields, the required tags, the tier, and any exempt sub-paths. Those clauses are declarations: nothing in the write path or the audit walk evaluates them, so pairing the field with the tag is a convention you keep rather than a check that fires.

How it operates — the write-time sequence

When you write a vault file, the frontmatter pillar runs these checks in order:

  1. Type allowlist. The type: must be in the merged registry. On a Strict-tier write an unknown type is denied, the error naming the allowed types and pointing to /govern register; a Standard-tier write proceeds with a warning.
  2. Required fields. The type's own required fields must all be present. Missing fields on a Strict type are denied with the list of what to add.
  3. Folder placement. If the type declares an expected folder, a mismatch surfaces an advisory (never a block) — cross-folder reference docs and customized structures legitimately diverge.

The librarian's coverage audits then walk the vault periodically and surface recurring drift — types whose required fields you keep declining, folders accumulating placement advisories, two files both claiming to provide one capability. Those surface at session close; you triage.

Tagging — the query surface

The gap in native Claude Code

Claude Code ships no tagging system at all, and Obsidian's native #tags are freeform — no grammar, no controlled vocabulary, no cap. Left ungoverned, tags fragment into near-duplicate variants within months (#urgent, #high-priority, #priorityHigh) and the graph that was supposed to help you navigate becomes noise. Nothing keeps the vocabulary faceted or bounded. The tagging pillar supplies the grammar and the ceiling.

Tags are the surface you query — they drive the graph view, the filter pane, and the maps-of-content you navigate by. They're decoupled from frontmatter on purpose: a file is legible to the system through its fields even with no tags, and legible to you through its tags regardless of the rest.

The grammar, and two classes of dimension

Every tag matches #dimension/value — a registered dimension prefix, then a kebab-case value (the full shape is ^#[a-z][a-z0-9-]*/[a-z0-9][a-z0-9-]*$). A tag whose dimension isn't in the allowlist is denied at write time, the denial naming the offending tags and the prefixes you may use, so you can pick from the vocabulary, omit the tag, or register a new dimension; the value half of the shape is a convention the write gate does not check. The flat freeform tag is rejected by construction — the dimension prefix is what keeps related values clustered and queryable.

ClassWhat it isWho stewards it · foundation ships
System-utilityMachine-emitted dimensions whose values are operational, not subjective.Skills, hooks, crons. Foundation ships #status/* and #log/* — cap-exempt.
User-facingDimensions you populate as you author and curate.You. Foundation ships #project/* and #library/*; your overlay adds further axes at onboarding.

The split exists because the two classes drift differently. System-utility values come from skills with stable vocabularies, so fragmenting them into near-match variants would split the operational graph; they're governed by a log-subtype registry with two protections — an audit-time canonicality pass (the librarian reports any #log/* or #status/* value with no registry entry, and flags two registered subtypes sitting within a couple of edits of each other) and explicit first-emission registration when a skill first emits a subtype. User-facing values come from you and grow with your work, so locking them at install time would force the foundation to guess your domain.

The 25-value cap, and why the number is 25

Distinct values across all user-facing dimensions stay under 25, and raising that ceiling is a deliberate tagging_cap_override carrying a written reason. Both are governance declarations you hold to: nothing in the shipped tree tallies your distinct values or refuses a widening. The ceiling is the working-memory limit on faceted vocabularies: past it, decision fatigue produces variant-creation rather than canonical-term selection, the vocabulary fragments, and your own recall collapses. The number isn't arbitrary; it's the point where a controlled vocabulary stops being one.

One more coupling: the folder-mirrors-tag invariant. A file in a structural cluster folder carries the cluster's #dimension/value tag, just as it carries the matching lineage field. Both sides are conventions rather than gates — the frontmatter check reads the type registry, not a cluster rule, and the tag check tests only the dimension prefix — and kept, they keep the folder hierarchy and the taxonomy aligned, so moving a file across clusters moves both.

How it operates — the write-time sequence

  1. Dimension allowlist. Every dimension must be in the merged allowlist; unknowns are denied, the message naming the offending tags and the prefixes you may use.
  2. System-utility canonical-value check. Values under #log/* and #status/* pass the write; the librarian compares them against the log-subtype registry at audit time and reports the ones with no entry.
  3. Tag presence. A non-exempt file with no tag surfaces an advisory — it flags a potential graph orphan at capture, and never blocks.
  4. Coverage watch. The librarian's tag-coverage audit walks the vault and reports files with no tags field and tags carrying an unrecognized dimension prefix.

Naming — filenames and paths as contract

The gap in native Claude Code

Claude Code reads whatever paths you hand it and imposes no filename or path discipline; plan mode creates artifacts with no naming contract. So filenames drift, slugs come in mixed shapes that consumers can't normalize, operational exhaust leaks into commit history, and the vault's first-level shape stops being walker-discoverable. The naming pillar makes the path itself part of the contract.

The system reads filenames and paths on every write — to decide whether a file belongs where it lives, to route plan-tree artifacts, and to keep exhaust out of git. The rules are quiet until a write would drift the structure, then they surface the drift before it lands.

The vault-root structure and slug grammar

A fresh Brain Stem vault is deliberately lean at the top. The scaffolder seeds two real folders — Vault Writers/ and Bases/ — authors the vault-root CLAUDE.md contract, and wires a set of symlink shortcuts to surfaces that live outside the vault. Everything else is yours to create as your work needs it.

At the vault rootWhat it is
Vault Writers/The catalog of systems that write into the vault.
Bases/Starter Obsidian Bases views over the typed frontmatter — a by-type list, a recent-notes view, and a status board.
CLAUDE.mdThe vault's orientation document — the one permitted bare file.
Plans/ symlink→ your plan tree (~/.claude-plans).
Skills/ symlink→ your skills directory.
Wiki/ symlink→ the universal Library.
Projects/ symlink→ the project binders.
Work/ symlink→ your deliverable work area (~/work); exempt from the vault's per-folder index mandate — though each project's deliverables/ and reference/ subfolders now get their own _index.md from a separate work-scoped pass.

The naming pillar enforces a documented-root allowlist: a file written at the vault root must sit in one of the documented names (or be the exempt CLAUDE.md), otherwise it draws a placement advisory pointing you to move it or register the folder via /govern register --kind folder. The allowlist additionally tolerates two optional conventional folders — Archive/ and Daily/ — if you keep that practice, but the scaffolder creates neither; they are permitted, not shipped.

Every slug — filename, folder, frontmatter id, plan prefix — follows one shape: [a-z0-9-], lowercase ASCII, digits, and hyphens. No spaces, no underscores, no mixed case, so every consumer can normalize identifiers without per-surface special-casing. The one human-readable root name (Vault Writers/) is a navigation surface — an explicit exception, not a license to deviate inside it.

Gitignore at-depth — a real leak

A gitignore pattern that should match at any depth (Tags/, node_modules/, .DS_Store) needs the **/ prefix. Bare-name patterns match only at repo root; deeper instances slip past — a production-scale bare-name bypass once leaked ~100 operational files into a reference deployment. The rule ships in the naming pillar — the **/ pattern grammar plus the ignore defaults the foundation applies to its own repo — with a pre-commit hook as the declared promotion path if drift recurs.

Plan slug discipline

Plan-tree files under ~/.claude-plans/ carry the strictest naming contract in the vault. Two rules fire at write time, and a third is checked when /new-plan creates the directory:

  • NN- numeric prefix — creation-order, never backfilled; the next plan takes one above the highest existing prefix, and gaps from retired plans stay as gaps.
  • Status marker — a **Status:** bullet, a status: field, or a status key in manifest.json; a plan with none is denied (the index walker would file it under "Unknown").
  • Shame-slug rejection — /new-plan refuses auto-generated filler like async-wiggling-donut (--force-slug overrides); a plan needs a descriptive slug that names the actual work.

Two sanctioned paths handle all three in one flow: /new-plan (ad-hoc scaffolding of the canonical quartet + manifest) and /backlog-research (the same, research-first). Hand-writing a plan directory usually fails one of the rules; a per-write PLAN_STATUS_OK=1 override exists for the rare deliberate case and lands in the audit log. Sub-plan artifacts at depth ≥ 3 additionally carry a parent_plan: field so plan-tree walkers resolve ancestry without parsing paths — a sub-plan's root artifacts are denied without it, while the wider population of files beneath them is reconciled at audit time, so an in-flight reorganization isn't trapped by the gate.

How it operates — the write-time sequence

  1. Root-or-exempt. A vault-root file must be in a documented root or the single-file exemption set; a new root path surfaces a placement advisory.
  2. Slug grammar. Every slug — filename, folder, id — follows the kebab [a-z0-9-] convention; the only write-time slug checks are the plan-tree gate (next) and the tag dimension deny, while ordinary filenames carry the convention without a write-time block.
  3. Plan-tree rules. A write under the plan tree checks the NN- prefix and the status marker (both deny), and denies a sub-plan root artifact at depth ≥ 3 that omits parent_plan:.
  4. Path-routing match. A write to a folder outside the documented set is matched against the declared folder patterns and draws a registration advisory; the lineage fields, tags and tier a rule declares are not evaluated at the write.

File-type contracts — the body schema

The gap in native Claude Code

The platform's write hook can allow or deny a save, but it carries no idea of a per-type body shape — no size caps, no required sections, and no notion that some files are create-only (must never be overwritten) or append-only (must never be replaced wholesale). So a routine regeneration can silently clobber a generated artifact, and there's no structural backbone a sweep can safely regenerate against. File-type contracts supply the body rules.

Frontmatter governs the YAML at the top of a file; file-type contracts govern the body — how long it may be, which sections must be present, and what the system may do to it at write time.

The matcher / parameter split

A contract has two pieces, declared apart from each other. The matcher declares which writes trigger this contract and lives outside the contract — in a sibling pillar (mandatory-files for vault mandates, plans for plan-tree files), or in the hook or skill that emits the file; a couple of contracts name no matcher at all. The contract declares what the body must look like: write_shape, size_limits, required_sections, prohibited_sections, frontmatter_enums, and any structured-body rules. The split lets one contract be reused across matchers and lets a matcher swap parameters without rewriting the contract — the same separation Kubernetes draws between ValidatingAdmissionPolicy and its paramKind. And because the rules live in data (the contract) rather than in the hook script, tuning a size cap is a data change, not a code change.

The write-shape enum

Every contract carries a write_shape — the field that states what a write may do to that file: create it once, replace it wholesale, append to it, or prepend a row.

ShapeWhat it permitsDefault class of files
create-onlyThe file is written once and later writes must not overwrite it.Generated registration records: writer descriptors, ADRs, ideation briefs, the vault-root CLAUDE.md.
replaceFull-file replacement on every write; prior content is snapshotted for diff-review.Files regenerated as a unit: _index.md, manifest.json, tasks.md, deliverables, Library articles.
append-templateWrites must append a templated block; the contract carries the template and any sentinel markers.Append-only records: handoff.md, spec.md sub-sections.

Overlay collisions and the override discipline

Because the overlay is union-read, it can shadow a foundation contract. The system permits it — but every shadowing entry must carry an _override_reason. On each overlay write a collision check runs; a shadow lacking a stated reason is denied with the offending entries enumerated. A per-write escape hatch (--force-override, or R52_FORCE_OVERRIDE=1 for direct edits) exists for bootstrapping or bulk import, but neither persists — the next write goes back through the gate. The discipline serves two ends: the reason travels with the divergence as a permanent audit trail, and the explicit bypass keeps casual overrides from accumulating silently.

How it operates — the contract checks

Unlike the first three pillars, the body contract is almost never a write-time block. The matcher resolves which contract a path triggers; two narrow rules are checked at the write — the contract's frontmatter coupling, and the section schema of a plan-tree handoff.md — and the rest of the body rules below are declarations the tools that write each file honour.

  1. Matcher resolution. The matcher pillar names which contract this path triggers; no matcher → no body contract applies (the file still validates against the type registry at write time).
  2. Write-shape. The declared shape records what the file permits — create-only forbids overwrites, append-template forbids wholesale replacement, replace regenerates as a unit. It is a declaration the writing tool reads, not a check the guard runs; create-only files route their edits through the file's amender by convention.
  3. Size limits. A declared size_limits.max_lines is a stated ceiling in the contract, not a write-time block — the runtime ships no synchronous line cap at all.
  4. Required / prohibited sections. One body-structure rule does fire at the write: a new session heading in a plan-tree handoff.md must match the contract's section schema or the write is denied (HANDOFF_SECTION_SCHEMA_OK=1 overrides). The other contracts' required and prohibited headers are not checked at the write.
  5. Frontmatter coupling. Contract-declared frontmatter requirements and frontmatter_enums are checked at the write — a vault-writer whose writer_kind or status falls outside the enum is denied by the guard; other types' contract enums are reconciled at audit time.

How the four pillars check one write

A single write to one vault file runs the four pillars in sequence — type, then fields, then placement, then tags, then the two body rules the guard checks at the write. The strict-tier checks deny; the rest teach.
