Build Your Own Capabilities

Brain Stem ships a skill, capability-building, for adding a capability of your own the deterministic way: pick the right kind of building block first, let a script write the files, and start from a fixture that fails. Everything you add lives where an upgrade leaves it alone.

Where your additions sit and why they survive an upgrade is on Extension points. The map of what your system runs is on The system map.

The idea: the model routes, scripts own the files

The skill is a route, not a template folder. Claude reads the one reference that fits the step you are on, and a script writes every file, so the shape of a record, a name or a directory is never typed by hand. A mistyped directory or a hand-numbered record is the kind of error a script cannot make.

Step one: choose the primitive

Claude Code offers several building blocks. The skill’s primitive-choice reference sets out when each one is right, and the rule that settles most choices is short: if a behavior must hold every time, it belongs in a hook. An instruction in a skill or in your project notes is a request, and the model can skip it under pressure. A hook runs whether or not the model cooperates.

Building blockChoose it when
HookThe action must happen the same way every time and needs no judgment from the model
Skill with scriptsThe model needs on-demand knowledge or a repeatable workflow, and a script can own the deterministic part. The default for everything else
SubagentYou want an isolated context, parallel work, specialized instructions kept out of your always-loaded notes, or a narrower set of permissions
WorkflowA script holds the order of several steps or agents, so the model does not re-decide it
CommandYou want to start a prompt on purpose, by name, every time

Add to a skill you already have before you create a new one. An idle skill costs only its name and description at the start of each session, and a split pays for itself only when it spares every use of the parent from loading material it did not need.

Step two: let scripts write the files

The scaffold writes the skill folder, the capability or the hook stub, and a failing fixture stub to start from.

CommandWhat it writes
scaffold.sh skill <name>The skill folder with a SKILL.md that uses only recognized keys, the empty scripts/ and references/ folders, and a failing fixture stub
scaffold.sh capability <skill> <cap>The capability script, its ## Capability: heading in the skill and its registry row, which move together, plus a failing fixture stub
scaffold.sh hook <name> --event <E> --matcher <M>The hook script, with a deny function and a silent allow path, and a failing fixture stub. It prints the registration entry and never edits settings.json; you register the entry yourself

The scaffold never overwrites anything, and a failed write leaves no half-made tree. A refusal exits 2 and the last line it prints starts capability-scaffold: refused:.

Step three: start from the failing fixture

The fixture the scaffold leaves prints FAIL: STUB and exits 1. Make it pass. Run each fixture red before the change and green after it, then break the change on purpose and watch it go red again. A refusal or a hook deny is worded as one line with the fix in it, and a fixture compares that line byte for byte. A script or hook you wrote is checked against a fail-loud list before it ships: nothing is swallowed, and a failure is impossible to miss.

Step four: validate, count the cost, register

  • Validate and evaluate. claude plugin validate --json reports a skill whose frontmatter does not parse, and claude plugin eval runs each case with and without your skill, so a capability that does not beat the baseline is not earning its context. Deterministic graders come first.
  • Count the always-on cost. The name, description and when-to-use text of every skill are paid at each session start, so keep them short and put the main use first.
  • Lint the frontmatter. skill-parity reports a key Claude Code does not recognize (it would be ignored without an error) and a skill whose description plus when-to-use text passes the 1,536-character listing limit. See Extension points.
  • Put it on the map. Run /librarian system-map --render and confirm your capability has a page. See The system map.

Plan gates that follow the shape the write guard expects

If you review your own plans, two commands handle the records and the reviewers. A gate record is a numbered review record in the plan’s gate-record folder, and the name pattern comes from the gate_records key of the plans rules. 

gate-record.sh write <plan-dir> --gate <1|2> --kind <kind> --body-file <path|->
gate-record.sh install-reviewer <project-dir> [--only plan-reviewer|build-checker]
  • write numbers the file, composes its name, writes the frontmatter, prints the path and never overwrites an existing record.
  • install-reviewer writes two reviewer templates, plan-reviewer.md and build-checker.md, into that project’s .claude/agents/. Each is limited to the Read, Glob and Grep tools, so a reviewer reads and reports and cannot edit. A file you already have is never overwritten. No agent joins the shipped roster: the copies are files of your own project, and they set no model, so pin one that differs from the author’s when you dispatch.

A review is worth having only when the reviewer is independent: a fresh context, a different model and read-only tools. A verdict from a reviewer whose tools failed mid-run is marked degraded and does not close a gate. A refusal from gate-record.sh prints gate-record: refused: as its last line and changes nothing.

Seeded permission

Install and upgrade offer one more permissions.ask rule, for edits under the skill’s folder, under the usual rule that each seeded rule is offered once. See Packaging & runtime.
