Write-time governance · rationale

Keeping the knowledge graph reliable

Baseline Claude Code can follow instructions and intercept supported tool calls, but it does not supply an information architecture or keep durable artifacts correctly shaped, placed, linked, and readable as the corpus changes. When those guarantees depend on memory and convention, drift becomes context debt. Brain Stem turns the native controls into layered governance: real-time guidance protects supported writes, while generated navigation, reconciliation, and audits maintain wider relationships.

Write-time governance

The governance engine

Guide writes before they become context debt. Claude Code can write files without imposing a knowledge-architecture contract on them. If those files are meant to remain discoverable and trustworthy as one corpus, conventions alone are not enough. Brain Stem's rulebook covers types, fields, placement, names, tags, links, indexes, and document relationships. PreToolUse is the prevention point for supported Edit and Write calls; post-write checks, close-time reconciliation, and periodic audits cover invariants that cannot be judged from one proposed file. The teach-gently, block-rarely posture is what unrelated policy systems converged on.

Intercept before the write (PreToolUse) when prevention is required Relying only on after-the-write feedback (PostToolUse) Modern PostToolUse hooks can inject corrective context and replace the tool output Claude sees, but the action has already happened. PreToolUse remains the supported point that can stop or reshape a tool write before it lands — the complete-mediation principle Saltzer & Schroeder. constraint
A stable policy vocabulary — allow, advise, deny Exposing raw hook mechanics independently in every rule Claude Code hooks support richer control than a binary gate, including allow, ask, defer, deny, input updates, and additional context CC hooks. Brain Stem's three verdicts are its own simpler governance semantics: advise maps to allowing the write while returning a targeted reminder. A missing tag earns a nudge, not a block. convergence
Advise by default; reserve hard denial for structural corruption Block on every imperfection (deny-first) Deny-first is hostile and trains people to disable the guard. Deny is kept for the few writes that would corrupt structure (an unknown document type, a malformed required field). The warn-then-block ladder is what OPA Gatekeeper, K8s Pod Security, and ESLint each reached independently. convergence
Let rules earn the right to get strict (data-gated) Asserting strictness on a hunch An advisory is promoted to a hard block only once real usage shows it rarely false-alarms — so it never retroactively denies older work. Matches the monitor-before-you-escalate practice of graduated policy engines OPA Gatekeeper K8s Pod Security. convergence
Fail open — a broken guard never locks you out Fail-closed (block on self-failure) A missing rulebook allows the write; a corrupt overlay falls back to foundation-only. Defensible because the engine governs content, not access authzed. It deliberately pulls against Saltzer & Schroeder fail-safe-defaults — an honest, domain-scoped exception rather than a security-control claim. convergence
Three tiers — schema, guard, safety-net — at deliberately different breadth Treating "the JSON schema" as the thing enforced at write-time The schema is the broad authoring contract; the pre-write guard is the narrow authoritative block; post-write and close-time verification form the advisory-but-broader net. A single hook sees one proposed tool call before it lands CC hooks, so full-shape conformance is too broad to block on without being hostile. constraint convergence
Keep rules as data in the bundle, read at runtime Hardcoding limits and enums in the hook body A limit — the MEMORY.md index cap, say — lives in a contract the guard reads, so tuning is a data change, not a code change. Hardcoded limits and enums would force a code edit for every tweak. convergence
Pair every hand-curated enforcement list with a gate-independent backstop Trusting deterministic gates alone A guard can be present-but-dead — non-executable and failing on every install, yet still invisible to deterministic gates that all read green. Because a dead guard passes every automated check, completeness assurance has to be gate-independent. convergence
