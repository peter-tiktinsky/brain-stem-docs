Knowledge graph & external AI

Every durable note in your vault carries a small, typed set of frontmatter fields — the cohort. That cohort is the substrate that makes the same vault navigable for humans (Obsidian), legible to Claude, and portable to outside AI tools (search, retrieval, graph) — without committing you to a heavyweight knowledge-graph product. This page explains what ships, what you can bolt on, and how to serve your vault to an external AI when you want to.

Where the frontmatter substrate ends and the ecosystem begins — a three-layer model, of which the foundation owns only the first.

The three layers

Think of the path from "notes in a folder" to "a corpus an AI can reason over" as three layers. The foundation ships only Layer 0 and points at good, off-the-shelf choices for the rest — so you are never locked into a single vendor or a schema you did not choose.

→

Layer 0 — the typed cohort (what ships)

A durable note carries seven fields. They are small on purpose: enough structure to be useful to every consumer at once, light enough that you are never filling in boilerplate.

  • type — what kind of note this is (an index, a deliverable, a reference article, …).
  • description — a one-line summary. It becomes a card subtitle in Obsidian and a relevance pre-filter for retrieval, so a tool can skim your vault without reading every file.
  • created and updated — real dates, in YYYY-MM-DD form.
  • tags — a controlled, prefixed vocabulary (a list, not a string).
  • id — a stable, readable slug that survives moves and renames, so an export or a server can reconcile a note to the same identity over time.
  • schema_version — an integer, so a future format change can target exactly the notes that need it.

Values are type-checked at write time by a lightweight format rule (a date looks like a date; tags are a list; the id is a slug; the version is an integer). That check warns, it does not block — the point is a nudge, not a wall. Obsidian's own property editor is seeded to match (dates render as dates, tags and aliases as lists) so the UI agrees with the governed shape. And because the cohort is just frontmatter, Obsidian Bases reads it directly: the foundation ships starter Bases views (all-durable-by-type, a per-status board, and a recently-updated view with the description as the card subtitle) that light up the moment your notes carry the fields — no plugin beyond Bases required.

How notes become compliant — three cooperating mechanisms

You should almost never have to fill the cohort in by hand. Three mechanisms cooperate so it happens organically:

  • Forward governance. A note created through the system — by Claude, by the workspace scaffolder, by the write-time hooks — is stamped compliant at creation: created today, a generated immutable id, a schema_version, and a description drafted for you (from the note's own first heading or opening line, at no AI cost; a cheap one-line model pass only when that heuristic is weak).
  • An opt-in auto-fixer. For notes that already exist — including ones you hand-wrote directly in Obsidian — a shipped capability backfills the cohort on demand: created from the file's first commit date (or its birth date), a generated id, the version, and a drafted description. It runs in a preview mode first, so you see every proposed value before anything is written, and you can trigger it as part of an upgrade.
  • A gentle default. Because the first two make notes compliant on their own, the shipped default only warns on a missing field. Any vault can dial itself up to hard-block once its backfill is done — that is a per-vault choice, not a default imposed on everyone.

Scope is location-based: the cohort applies to every note inside the vault, including folders symlinked in (like your work surface). Machine files the system parks outside the vault (logs, state) are out of scope by location, not by type.

Layer 1 — enrichment (you opt in)

Two categories of Obsidian plugin turn the flat cohort into something more graph-shaped. The foundation endorses them and does not bundle them, so you stay in control of what runs in your vault:

  • Typed relations — a plugin such as Breadcrumbs reads relationship fields in your frontmatter (parent, up, next) and renders a real navigable graph and breadcrumb trails over them.
  • Semantic similarity — a plugin such as Smart Connections computes embeddings so "related notes" is by meaning, not just by link. It complements the cohort; it does not depend on it.

Layer 2 — serving the vault to an external AI

When you want an outside AI assistant to answer questions over your vault, you serve it — you do not rebuild it. Two shapes cover almost everyone.

Live queries — an MCP server over the vault

The Model Context Protocol (MCP) lets an AI client call tools against your vault: search frontmatter, follow links, read a note. The recommended default is the cyanheads obsidian-mcp-server — it works directly against the vault's files and frontmatter, which is exactly what the cohort makes queryable, and it does not require Obsidian to be running.

  • If you specifically want a permalink / AI-memory model (stable note URLs an assistant can cite and write back to), basic-memory is the better fit.
  • Avoid making mcp-obsidian your default: it drives the app through the Local REST API plugin, so it needs that plugin installed and Obsidian open — more moving parts for the common case.

Batch corpora — a CLI exporter for RAG / GraphRAG

For retrieval-augmented generation or a graph pipeline, you do not need a live server — you need a clean, one-shot export. A CLI exporter walks the vault and emits a corpus (the note bodies plus their cohort frontmatter as structured metadata) that a RAG or GraphRAG toolchain ingests. Because every note already carries type, description, id, and dates, the export needs no per-tool adapter — the metadata a retriever wants is already there.

Interchange formats — only at the boundary

Formats like schema.org / JSON-LD (and the broader Open Knowledge Foundation vocabularies) are for publishing and exchange, not for how your notes are shaped day to day. Map to them at a publish or export boundary if a downstream system asks for them; keep your native frontmatter simple and human-first everywhere else. This keeps the vault legible to you and to Obsidian while still being able to speak a formal vocabulary when it has to.

The through-line. Own Layer 0 well — a small typed cohort, applied consistently — and every other layer becomes a choice rather than a rebuild. Humans get Bases views, Claude gets legible context, and an external AI gets a corpus it can serve, all from the same seven fields.
