Knowledge-Graph Extendability

A knowledge graph is a map of your information that records how the pieces connect: which research informed which decision, which plan produced which deliverable, which project a file belongs to. Brain Stem's folder and file architecture builds that map as you work, out of ordinary files. That graph is what Claude Code reads through Brain Stem's own hooks and skills — and it is deliberately shaped so that any other harness or model can read it too. Search and retrieval are already there when you work in Claude Code; this page is about what makes the graph legible to anything else, and the routes people take to extend it.

Brain Stem ships the substrate and the blueprint, not a search engine or a server. Extensions are yours to add, and the architecture makes adding one a small step rather than a rebuild.

Independent of the application you read it in

The corpus is plain folders, Markdown files with YAML frontmatter, and JSON. It works identically whether you open it in your Markdown editor of choice, your default text editor, or never open it at all. Brain Stem reads and writes the files directly, without any platform-specific tooling. The relationships that make it a graph live in the files.

What the governed corpus gives a machine reader

Each convention below is enforced or maintained by Brain Stem for its own reasons — routing, auditing, capture. The right-hand column is what the same convention hands to any reader that is not Brain Stem: a second harness, a local model, an index you build.

ConventionWhat shipsWhat it affords a reader
Typed frontmatter Every governed file declares a type; a cohort of identity fields (description, created, updated, tags, id, schema_version) is required per type, with the exact set declared in the governance registry (The single document). Metadata that parses deterministically into filter columns. A one-line description is a relevance pre-filter that survives chunking; id is a stable identity across moves and renames; created is never minted as "today", so dates mean what they say.
A bounded tag vocabulary One grammar, #dimension/value, over a declared set of dimensions; system values are enumerated, near-misses refused, the user-facing vocabulary capped. A facet vocabulary small enough to enumerate and clean enough to filter on: a tag filter returns a bounded, meaningful slice rather than a drift of near-synonyms.
Addresses, not app-resolved links Every link the system writes is a relative Markdown link to a path. Wikilinks in your own prose are accepted, checked for dangling targets, and convertible to the path form on request. A link a program can follow with nothing but the file system. A wikilink resolves through an application's index by name; a path needs no index and no guess about which same-named file was meant.
Stable chunk boundaries Headings structure every governed document; exactly one frontmatter block is permitted per file, at the top. A chunker can split on headings, carry each heading as the chunk's label, and strip metadata without mistaking a second YAML block for content.
A triage surface in every folder Every non-exempt folder carries a generated _index.md: a folder-context paragraph and a contents table of each file's link, length, type and description. A reader orients at any level of the tree from one small file, and descends only where the summaries warrant.
One tree with declared shortcuts The brain folder joins the plans tree, the project binders, the library and your work spokes through symlinks at its root, so one logical tree spans surfaces that live elsewhere. One root to walk. Resolve each file to its physical path, keep the first occurrence, and the whole corpus is indexed once with no duplicates and no surface left out.
Immutable identity Once a file carries created and id, the system never rewrites them; a rename records its history rather than breaking the trail. An external index reconciles a file to the same identity over time, so a rebuild updates entries instead of orphaning them.

The blueprint ships with the corpus

A knowledge base is only extendable if its structure is written down somewhere a program can read. Fortunately, Brain Stem ships this information in a model-agnostic package.

Brain Stem governance provides consumers with a summary layer of consolidated indexes and ledgers to enable efficient information routing corpus-wide. Further, all governance hooks and skills run leveraging structural blueprints that Brain Stem maintains outside the corpus itself. These additional assets provide comprehensive documentation on the knowledge graph's architectural organization, content conventions, and management processes. All together, these resources enable an external model to immediately situate itself in your brain folder and effectively navigate your file structures.

Inside the corpus — the summary layer, generatedEvery folder's _index.md; the plan index, backlog and inbox roster; each project binder's situating card, research index, decision log and handoff chronicle; the library's topic indexes. All derived from their sources, never hand-tended, always consistent with what they summarize.
Governance registries · JSONEvery file type and its required fields; the tag dimensions and their allowed values; the recognized folder roots and naming rules; the folder-index mandate; cross-document relationships; a contract per file type — composed into one bundle the hooks read at runtime (The governance engine).
Schemas · JSON SchemaThe shape of every structured file in the tree: the plan manifest, the plan artifacts, and the memory files.
Maintained graph state · JSON + NDJSONThe librarian's manifest records the cross-reference graph, the file inventory and the tag census as it audits; nearly every audit emits its findings as newline-delimited JSON.

The summary layer lives in the corpus and points into it; the three blueprint assets live in the install and describe it.

An indexer, an exporter or a second harness does not have to infer the corpus's organization from its contents. It can read the map — and because the map is the same one the governance runs from, it is never stale relative to what the hooks enforce.

A note on Obsidian

Brain Stem's creator opens the brain folder in Obsidian: its simple interface is pleasant to navigate, and the corpus is readily Obsidian-compatible. That is a preference about the reading experience. No part of Brain Stem's design, build, or functionality depends on Obsidian, and it functions just as well without it.

Routes people take to extend it

Four extension options, each something you add on top of the corpus. For each: what it is, when it earns its place, and the one thing to get right when you build it over Brain Stem.

Your governed corpusplain files + the blueprint
→
Read-only accessanother model or harness reads it as reference
Retrieval indexsearch by meaning across everything
Relationship graphask what connects to what
Boundary adaptera server or interchange format, only if demanded

The corpus is the one starting point; the four that follow are alternatives, not stages — you add whichever earns its place, in any order, or none of them.

Read-only access for another model or harness

What it is. Pointing a second model, or a different harness, at the corpus as read-only reference material. Because the corpus is plain files with a map, any tool that can read a folder can do this today.

  • When it helps: navigating or chatting with your whole corpus from another tool; a second model's read on your own material; a model whose strengths differ from the one you work in.
  • The Brain Stem consideration: read-only means read-only. Write-time governance lives in Claude Code's hooks, so any other writer bypasses every gate — and a tool that "tidies" a frontmatter block or rewrites a link forks the corpus from its governance silently.

A retrieval index

What it is. An index of the topics and concepts that appear across your entire corpus, built by embedding the files' contents, and a search skill over it that retrieves approximate answers quickly across disjoint surfaces without reading files. This is the vector-search shape most people mean by "RAG".

  • When it helps: asking a question whose answer is scattered — every time I have tackled this category of problem, across all my projects, what setup did I use and what worked?; scoping a research topic before committing to it; tracing a trend across projects that never referenced each other.
  • The Brain Stem consideration: resolve the symlink hub to physical paths and index each file once, or much of your embedding work goes into duplicates. Keep the index outside the governed trees as a derived replica that only ever reads. And do not reinvent the chunking: the headings, the single frontmatter block and the identity fields already give you chunk boundaries and filter columns. Brain Stem's creator built exactly this over their own corpus — heading-split chunks, frontmatter as metadata, a small open-licensed embedding model served locally, ranked and path-cited results — without inventing a single new convention.

A relationship graph

What it is. A structure that records which items connect to which, and how, so you can ask connection questions rather than similarity questions: which decisions cite which research, which plans touched which project, what a finding went on to influence. A retrieval index answers "what is like this"; a graph answers "what is connected to this, and through what".

  • When it helps: tracing the lineage of a decision back to its evidence; finding everything a piece of research went on to shape; seeing what a project depends on before changing it.
  • The Brain Stem consideration: the edges are already declared, so build from the declarations rather than extracting relationships from prose (where such pipelines usually go wrong). Plan manifests name their research artifacts, decision records and parent plans; every generated link is a path; tags are a bounded facet set; each project binder is a hub.

A boundary adapter — a server or an interchange format

What it is. A server that exposes the corpus to a client over a protocol such as MCP, or a mapping of the frontmatter onto a formal vocabulary such as JSON-LD.

  • When it helps: only when a specific downstream system demands that shape. Nothing above requires either.
  • The Brain Stem consideration: keep the native files simple and human-first and translate at the edge. Run search and retrieval over the plain Markdown directly rather than making a server a mandatory intermediary between you and your own files.
Warning — never launch a Claude Code session from the brain folder

Launching from the corpus puts the entire corpus in the session's scope. That risks polluting per-project memory and context, and it spends tokens on material the session does not need. Launch every session from the project you are working in; the corpus is reached through the project binder's pointers (What loads each session).

The through-line

Brain Stem governs files and folders so that its own hooks can read them deterministically. Typed metadata, addresses instead of app-resolved links, an index at every level, a machine-readable map of the whole: every one of those guarantees is exactly what an outside reader or a retrieval layer needs too. Extending the graph means pointing something new at conventions that already hold.
