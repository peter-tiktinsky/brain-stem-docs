Sessions · keeping your place

Checkpoints

A long session fills its working window, the platform compacts the history into a summary, and the verbatim detail is gone. A checkpoint is the autosave for your train of thought: a small structured file that captures where you are, so a compacted session can pick up exactly where it left off.

One file per session: ~/.local/state/brain-stem/sessions/<session-id>/checkpoint.md.

Context pressure — the fuel gauge

Context pressure is just how full the working window is, as a percent. The fuller the tank, the more urgently the system asks you to save your place. It's a ladder, not a single alarm:

~35% · autosavea lightweight checkpoint is written silently, if none is fresh
›
~45% · warning bannershown to you once: "at your next natural break, run /session-checkpoint, then /compact"
›
~48% · urgent bannershown to you once: "run /session-checkpoint now, then /compact" — or start a fresh session
›
~48–90% · stop-gaterefuses to let the session end without an adequate checkpoint
The banners, precisely → each banner appears once when the gauge enters its band, not on every message; leaving the band and coming back shows it again. The banners are a percentage of the window at which the platform auto-compacts, so a smaller auto-compact window brings them earlier. The banners go to you, not to the model: nothing forces a checkpoint mid-task.
The stop-gate, precisely → in the ~48–80% band a full Continuity Block lets you stop at any age, while a lighter checkpoint must be fresh (<10 min); in ~80–90% any checkpoint will do; above ~90% a safety valve always lets you stop (the window's too full to keep working anyway).

What a checkpoint holds — the Continuity Block

The checkpoint follows a fixed schema, the Session Continuity Block. Nothing is silently skipped — a field that can't be filled is marked [MISSING] rather than dropped. The first three fields are written as plain single lines on purpose: the pre-compaction hook counts them to recognize a rich checkpoint and avoid clobbering it, at any age. A block the pre-compaction hook extracted itself is marked with its source and never counts as rich, so the next compaction refreshes it instead of carrying an old snapshot forward. 

# Session Continuity Block
plan_id:        the active plan
phase:          where in it
task_id:        current task + status
## completed_steps     what's done this session
## files_modified      absolute paths touched
## key_decisions       choices made + why
## next_steps          the ordered resume
## ac_status           acceptance-criteria checklist
## current_blocker     the live blocker, if any
context_pct_at_checkpoint:   the gauge at write time

Three writers, one file, richest wins

Three things can write the checkpoint, and they have a precedence so the richest snapshot always survives — all target the same file:

WriterWhenRichness
/session-checkpoint skillOn request — the banners recommend it, and the stop-gate asks for itRichest — the full block
The per-message hook~35% autosave, only if none is freshLightweight
The pre-compaction hookJust before compaction, unless a full block from the skill is thereMechanical fallback — no model call; refreshed at each compaction
Why save and restore are split across two moments

The save must happen at compaction — that's the last moment before detail is trimmed. But the restore can't: the platform doesn't allow a script to inject context back into the conversation at the compaction moment. So restore happens at the next session start — the harness restarts the session marked "compact," and the start hook reads the checkpoint back in verbatim, leaving the file in place so the saved state survives the boundary. Archiving happens later, at the next checkpoint write: the outgoing checkpoint is copied to a dated archive before the new one replaces it (a copy first, then the swap — so a failed archive never loses the outgoing content, and prior state is kept as history). It's the write-ahead-log recovery pattern, forced by which moments may inject context.

That restore is about this work thread — which plan, which task. Separately, a second hook runs at every session start (not only after a compaction) and loads a short project-orientation card: the plan roster, the project's overall status, the active focus, and the latest handoff headline — so the session also knows what project it is in and where that project stands. The two answer different questions; the card lives with the project binder.

Reference

  • Checkpoint file — ~/.local/state/brain-stem/sessions/<session-id>/checkpoint.md (one per session).
  • Writers — the /session-checkpoint skill (richest; atomic write + verify; failure mode is block-and-log; the writer behind it is checkpoint-gather.sh), prompt-context.sh (~35% autosave + the two banners), pre-compact-checkpoint.sh (fallback extract).
  • Stop-gate — stop-checkpoint-check.sh uses exit code 2 to keep a session going until the checkpoint is adequate for the band. Where the ladder allows the stop, the stop hook also runs the library-promotion candidates arm of library-scrub when the live mode is set: prompt asks once per close, auto answers, and an unset mode reads off, so there is no prompt and no model call (the library_promotion setting). In auto mode the claim and its answer are taken under one lock acquisition, so lock contention leaves the promotion never claimed and the next stop offers it again.
  • Thresholds — the warn/mandate banner percents are settings-driven and measured against the auto-compact window (CLAUDE_CODE_AUTO_COMPACT_WINDOW, else autoCompactWindow in user settings, else the model window); the autosave and stop-gate bands read the raw gauge and are fixed in hook code (the session-continuity rule set). For a non-Anthropic model the window resolves from that auto-compact setting, else a 64,000-token default raised to the covering tier when the session's input is larger, and the pressure file reports which rule applied as window_basis.
  • Project orientation at session start — session-start-project-context.sh (the newest SessionStart hook) loads the project's situating card (_situating.md) as context before the first turn, on every session start; advisory and fails open. Distinct from the checkpoint: the checkpoint carries this work thread's state, the card carries project-wide orientation. See The project binder for the card's content and lifecycle.
