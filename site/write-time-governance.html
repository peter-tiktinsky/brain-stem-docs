Write-Time Governance

Every file the assistant writes in a governed tree — your vault, the plan tree, your Work projects — is checked, the moment it is created or edited, against a rulebook of conventions. A file put on disk by a shell command instead is not checked at write time. The point is that files are always discoverable by Claude and findable by you — not because someone remembered to apply the right format, but because the system enforced it at write time.

Conventions applied structurally — at the write — not left to memory or discipline.

What Claude Code gives you — and what's missing

Natively, Claude Code can follow scoped instructions and intercept supported tool calls with hooks. Interception is not the same as an information architecture: nothing native keeps durable artifacts correctly shaped, placed and linked as the corpus changes, so those guarantees are left to memory and convention — where they decay into drift.

Two kinds of governance

Brain Stem uses the word "governance" in two distinct places, and it helps to name them cleanly before going further:

This section

Write-time governance

Conventions that apply to every file and folder at the moment of creation: frontmatter schema, naming rules, mandatory indexes, doc-dependency chains. Enforced by a hook that fires on every write. The goal: any file the system touches is structurally legible immediately, without a cleanup pass later.

Project management section

Process governance

Conventions for how work is organized and tracked over time: plans, orchestration, project binders. These govern the lifecycle of work — how you propose, run, gate, and close a piece of work — not the shape of the individual files it produces.

The distinction is practical: if you are looking at a specific file and asking "is this well-formed?" or "why is this folder structured this way?", that is write-time governance. If you are asking "how does this piece of work get planned and run?", that is process governance in the Project management section.

What falls through the write — and what closes the gap

The write-time hook sees exactly one kind of event: an edit or write made through Claude Code's own file tools. That is deliberate, and it leaves four vectors it structurally cannot see:

  • Shell writes — a command that copies, moves, or writes a file from the terminal, by design outside the hook's matcher.
  • Scheduled and capability writes — the librarian's own renderers and any background job write through ordinary file IO, never through the hook (which is also what keeps them from deadlocking against it).
  • Edits made in another application — a note changed in your editor, or a file touched by a sync client.
  • Multi-file invariants — a rule that spans several files (a registry, its contract and its hook moving together) cannot be judged one write at a time.

Rather than widen the hook, Brain Stem pairs it with an audit tier: sweeps that walk the corpus after the fact, detect what the write could not, and either repair mechanical drift or surface findings for you. Most of them run automatically from session close, each on its own daily or weekly rolling window, or in a full librarian run:

GapAudit / repair layerPosture

The division of labor is the same everywhere: a machine-owned surface is regenerated or auto-corrected, a human-owned surface is reported on, and nothing in the audit tier rewrites prose you wrote.

Extending or overriding the rules

The write-time rulebook is sealed in a foundation layer — you do not edit it directly. You extend it (register new file types, folder types, writers) or override a shipped rule (with a stated reason) through the overlay seam. That is a personalization concern, not a write-time concern.
