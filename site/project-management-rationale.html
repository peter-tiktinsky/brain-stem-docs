Project management · rationale

From idea to durable execution

Baseline Claude Code can persist plans and tasks and coordinate agents, but those primitives do not form a durable lifecycle from raw idea through research, decision, execution, verification, and reuse. Without one control model, duplicate ideas survive, evidence separates from the work, and status becomes difficult to trust across sessions. Brain Stem supplies a reconciled inbox-to-plan path, an executable control file, independent verification, and a generated project binder.

Project management

Project organization

Project organization anchors the two kinds of work a project can hold: coding work lives in code repositories, where Claude Code is already at home, and non-coding work gets its own durable, governed home under ~/work/. Both surfaces receive the full Brain Stem treatment — memory, the project knowledge base, plans, the library, governance — and both roll up into the project binder. The organizing decisions that are Brain Stem's own (project identity by launch directory, automatic binder membership) sit with the binder section below.

Plans

A Brain Stem plan is built for durable execution: it is both an execution contract and a durable node in the context graph — it carries a fixed goal, machine-readable state, tasks and dependencies, research, decisions, and a handoff. Formal multi-step planning remains opt-in; many tasks do not need it. When work does earn that structure, the design aims to prevent false completion, forgotten direction, and one-off research that disappears when execution ends.

Orchestration & scheduling

When a ready plan runs, orchestration keeps parallel work untangled and completion honest: the manifest, dependencies, scoped worker briefs, circuit-breaker, and independent verification give orchestration helpers explicit state and failure controls rather than asking autonomous workers to infer the plan from prose alone — and a human stays in the loop at every irreversible step.

Brain Stem choseoverbecauseground
Route Brain Stem sub-plan reporting through the master Using Claude Code's agent-team model with direct teammate messaging for this workflow Claude Code now supports direct inter-agent messaging in experimental agent teams, so this is a deliberate Brain Stem governance choice rather than a platform limitation. For manifest-driven plans, bounded report-up edges reduce the tangled web that is a leading cause of multi-agent failure — ~37% of failures are inter-agent-misalignment (coordination) failures MAST. The master/sub flow maps onto the orchestrator-worker pattern, while native agent teams remain available when direct peer coordination is the better fit CC sub-agents. convergence
A human-gated runner that proposes and waits A fully autonomous, unattended daemon No task fires without a human reasoning or approval point — irreversible tasks halt for approval (human-in-the-loop), reversible ones proceed under supervision. An unsupervised runner inherits documented multi-agent failure rates MAST; it is built on the platform's headless mode headless mode. convergence
Enforce through Claude Code's own hooks, in three layers Prose standing-instructions, a single write-time blocker, or an async-only reconciler Hooks fire regardless of whether the model cooperates; prose decays over sessions #33603 #56393. A single blocker can't see cross-file invariants; an async-only sweep leaves a spec-gaming window. Every Edit and Write goes through one doorman — complete mediation over that surface Saltzer & Schroeder. convergence
Require a minimum safe dispatch envelope and evidence-gate additional controls Requiring every possible dispatch control regardless of demonstrated need Pre-dispatch scoping, brief-lint, a circuit-breaker, and an independent human gate address known coordination and false-completion risks. Budget caps, a standalone verifier, and mechanical retry belong only where telemetry shows that their added complexity closes a real gap. convergence

The project binder

The project binder turns plan output into project orientation. The decisions below govern how the binder is maintained and how project context reaches a session, and all three serve the same goal: keeping project state correct with no manual upkeep. The load-bearing thread is the same one that runs through the whole context pillar — auto-generated surfaces survive while hand-maintained ones rot.

Brain Stem choseoverbecauseground
The project binder is generated, never hand-written; membership is automatic A hand-maintained "project status" file and membership roster A status file kept current by a person rots the moment attention moves on. Deriving the binder from the project's plans keeps it correct with no upkeep — the central rot mode the system exists to kill, mirroring PARA's active-binder split PARA. convergence
A generated, automatically-loaded situating card (_situating.md) as the eager project-orientation surface Relying on a hand-curated cover page as the eager session-start surface — a file nothing automatically writes, so every fresh project would begin with a guaranteed read-miss The session-start context channel is the only way to inject project orientation before the model's first turn without user action. The card is regenerated atomically every session from machine-derivable fields alone — plan roster, per-plan status, active focus, latest-handoff pointers — so there is nothing hand-maintained to rot, and it is kept small so it never competes for the context window. The card is the binder's one cover; the deeper indexes behind it stay read-on-demand. convergence
Project identity is the launch directory, resolved through a tool-maintained anchor registry A hand-edited membership list A hand-edited roster drifts the moment you forget to update it; registering a project writes its launch-directory anchor for you, and a directory under no registered anchor degrades to a shared catch-all rather than mis-attributing. Johnny.Decimal is flagged an anti-pattern precisely because fixed addresses fight auto-membership binders Johnny.Decimal. convergence
