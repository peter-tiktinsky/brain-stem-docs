Configuration

Brain Stem has few knobs, and that is the design: nearly every configuration question is settled at one inspected moment — when you install or upgrade — instead of being discovered later when something behaves unexpectedly. This page is the single place that answers "where does this knob live?" for the whole system: the environment variable that picks the install location, the installer's flags, the rule for how its settings join yours, and the handful of switches that matter while it runs.

Why configuration is concentrated at install time — the reasoning, not the roster — is on Packaging & runtime: why configuration is settled at install time.

Where the install lands — CLAUDE_HOME

Claude Code reads everything it loads — settings, automation scripts, skills, rules — from one folder. By convention that folder is ~/.claude in your home directory; the CLAUDE_HOME environment variable is the override that says "put it somewhere else" (useful for trying an install in a throwaway location). The safety asymmetry around it is deliberate:

ModeIf CLAUDE_HOME is not setProvenance
Dry run (bash install.sh)Assumes ~/.claude to render a plausible preview, and records a claude_home_defaulted flag disclosing that it guessed. A preview writes nothing, so a sensible default is harmless.Built on native
Apply (bash install.sh --apply)Refuses — hard failure, exit code 10, nothing written. Real files must never land in a folder you did not consciously choose.Brain Stem specific

Install flags

Flags are how you consciously step around a guard — each is its own acknowledgement with its own refusal, so there is no single blanket "I know what I'm doing" switch. The dry run tells you everything it would need from you in one pass, under required_overrides, before you commit to anything.

FlagWhat it doesWhen you would touch it
--applyTurns the write-free preview into the real install.After reading the action plan — every real install or upgrade.
--upgradeThe one-command upgrade lane: asserts an install is present, resolves the install home itself, prints the upgrade plan.Every upgrade; there is no separate upgrade command to learn.
--force-installAcknowledges you are installing over content Brain Stem did not put there.Installing into a home that already has a Claude setup.
--i-understand-overwrite-riskThe typed confirmation that pairs with --force-install; without it, an apply that would overwrite foreign content stops instead.Same moment as --force-install.
--backup-dir <path>Names the folder where anything about to be overwritten is copied first, so nothing is lost.Whenever you are overwriting anything you care about; upgrades derive one for you.
--retrofit-existingAcknowledges that a plan tree already exists under ~/.claude-plans. The installer never touches your plans; the flag only confirms you have seen them.First install onto a machine that already has plans.
--migrate-majorThe explicit acknowledgement required to cross a major version boundary.Rare — only when a release notes say a major-version step needs it.
--frontmatter-fixOpt-in backfill that repairs missing typed frontmatter on existing notes during an upgrade apply. Default off; nothing auto-forces it.Bringing an older vault up to the typed-fields cohort.
--no-preserve-configOpts the install out of preserving an existing claude-mem plugin's configuration entries in settings. Refused up front (exit code 11) unless paired with --force-install.Rare — deliberately replacing a claude-mem setup.
--force-allA blunt clobber escape from an earlier era. Modern upgrade lanes refuse it outright; it survives only on fresh installs, where you almost never want it.Effectively never.

Onboarding's vault build has its own guard. It refuses to scaffold into a non-empty directory that is not already a Brain Stem vault, and says to pass --force or to point --vault-root at an empty directory. There is no flow that retrofits a foreign vault.

The settings merge rule

Claude Code reads one config file, settings.json, and the installer deep-merges the foundation's entries into yours rather than overwriting. Four properties of that merge are the whole story:

PropertyWhat it means for you
Field by fieldKeys you already set are joined, not replaced — the foundation's entries arrive beside yours, not instead of them.
AtomicThe merge fully succeeds or leaves your original file untouched; a half-merged settings file cannot exist.
No silent deletionIf a merge would silently drop a key you already set, the installer refuses to proceed instead.
Ask rules, offered onceInstall and upgrade append rules to permissions.ask — one for each top-level directory the installer manages and one for each skill it ships — so Claude Code asks before it edits a directory that every upgrade replaces. Each rule is offered once, and the install keeps a record of what it offered: a rule you remove is never added back, and a rule a later release adds is offered on that upgrade. Your own allow, deny, ask and defaultMode entries are never removed, rewritten or reordered; the seeded rules go after them.

Before any destructive step, a timestamped copy of your current settings is taken (settings.json.pre-install-<timestamp>) into a backup the installer can prove works. The two top-level configuration files, settings.json and settings.local.json, sit outside the install receipt by design — which is also why uninstalling removes them by name and your copies live on in the backup.

Switches while it runs

A small set of environment variables change behavior after installation. None of them needs setting on an ordinary install — each is either an acknowledgement for a deliberate exception or a location override.

VariableWhat it changesProvenance
CLAUDE_HOMEWhich folder the install (and Claude Code) treats as home; defaults to ~/.claude. See above for the dry-run/apply asymmetry.Built on native
MANAGED_SURFACE_OK=1Acknowledges a deliberate edit to an installed, receipt-listed file (a temporary live test you will port back). By default the write guard denies an in-place edit of such a file (MANAGED_SURFACE_PHASE reads 2-blocking); this acknowledgement lets the deliberate edit through, and acknowledged uses are recorded locally. Set MANAGED_SURFACE_PHASE=1-advisory and the guard instead draws an advisory naming the surface and the sanctioned route and allows the write.Brain Stem specific
PRE_ASQ_GUARD_DQ_PHASEThe decision-quality gate's posture. The shipped default is blocking; setting it to 1-advisory switches the gate to advise-and-continue for adopters who do not want the denial posture.Brain Stem specific
VAULT_WRITER_STATE_ROOTRelocates the durable root of the vault-writer system's state (the write-activity database). Defaults to the durable XDG location, ~/.local/share/brain-stem/.Brain Stem specific
LAUNCH_PROMPT_MAX_WORDSThe word count above which a handoff’s launch prompt draws a warning, from the write guard as you write it and from the session-close handoff check. Defaults to 300; a non-numeric or zero value falls back to 300. The warning never blocks the write or the close.Brain Stem specific
CLAUDE_MEM_DISABLE_OK=1Escape hatch that acknowledges a deliberate removal of the automatic memory-consolidation hook from settings; without it, the write guard denies that edit to protect the recall layer.Brain Stem specific

Where a switch guards a behavior documented elsewhere, the behavior's page carries the detail: managed surfaces for MANAGED_SURFACE_OK, the decision-quality protocol for its phase knob.

Setting one field from the command line

Some settings are a single field in a JSON record you would otherwise edit by hand. One setter, field-set.sh, writes them: it validates the value against the record's own schema, writes atomically, and leaves the file byte-identical when it refuses. It covers user-manifest set (one scalar in your user manifest), settings hook off and on (turn a hook off or back on), settings env set (an environment entry in settings), plan set (a plan's status, paused reason or disposition) and capture-freeze open or lift (a spoke's capture freeze).

  • Turning off a hook the installer requires prints a note that the next upgrade puts it back.
  • Turning a hook back on restores each entry at the position it held before.
  • A plan set status=completed applies the session-close rules first, in order: the ordering gate, the research declaration, then one atomic write, and the plan binder and task list re-render afterwards.
  • A path flag given an empty value is refused.

Exit codes: 0 done or a documented no-op; 2 refused with nothing written, on a line that starts field-set: refused:; 3 refused by a governance gate (the close ordering gate, the claude-mem protection that keeps settings hook off from removing the memory-consolidation hook, or a capture freeze that is already open); 75 lock contention, reported loudly and never skipped silently. Where lockf is installed, every write takes one kernel-backed lock (and runs unlocked where it is not), so two concurrent callers cannot overwrite each other's field.

Where your data lives

Configuration questions are often really location questions, so the map in one breath — three places, on purpose, so program churn never endangers your work:

WhatWhereChanges with
The program — scripts, skills, settings, rules~/.claude (or your CLAUDE_HOME)Install and upgrade
Your plans — project planning trees~/.claude-plans/Never touched by install, upgrade, or uninstall
Runtime state — working data the scripts produceOutside the program folder: durable ~/.local/share/brain-stem/, ephemeral ~/.local/state/brain-stem/Lives on across reinstalls

Changing behavior: the overlay

Most "configuration" in the everyday sense — new folders, file types, tags, writers, project work areas — is not a flag or a variable at all. It is registration: you add what you want through the overlay (/govern register), and your additions extend the shipped foundation without modifying it. That is the knob that survives every upgrade: the foundation stays exactly what its receipt describes, and your customization rides on top.
