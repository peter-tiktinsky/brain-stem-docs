Introduction

Introducing Brain Stem

Brain Stem provides the foundations for a personalized Claude Code operating system at install. From the moment it lands, the assistant remembers your work, organizes what that work produces, and starts every session already oriented to your projects — so long-term memory, project planning, write-time governance, session management, and information capture run as one maintained whole instead of separate pieces you wire up and keep alive yourself. It is built for anyone who works with Claude Code regularly, coding or not.

Claude Code ships out of the box with powerful capabilities and configuration tools — but the configuration itself is left mostly to you. Without heavy lifting on your part, the result is a disjointed system that never quite leverages those capabilities in unison. Brain Stem supplies the connective tissue: the support and governance systems that turn the blank slate into an interconnected engine, so you spend more time executing work efficiently and less time organizing your projects and reminding Claude how to behave.

This page is the gateway into the documentation for all of it: Orientation — this opening section, completed by the three cards below — frames the system and the case for adopting it, Getting started covers adoption, the six Architecture & capabilities sections document each capability in depth, and Reference holds the look-ups. The rest of this page walks through what Brain Stem ships, shows the whole system in one picture, and maps where its durable knowledge lives; every page is listed in the documentation map at the bottom.

The capability suite — wired into how your system runs

Context & memory

Self-organizing memory & knowledge

Claude organizes its own memory and knowledge — and weaves them into each other automatically, instead of leaving them as separate piles.

  • Memory that survives, split three ways — semantic, procedural, and episodic notes, at project and universal scope, read back at the start of every session.
  • A context library — reusable reference plus per-project binders that frame the work and never go stale.
  • Operational and contextual, kept connected — how Claude should act and what the work is, distinct but woven together rather than dumped in one bucket.
  • Lessons across arenas — a lesson learned in one project is promoted into universal rules and reference, so learning transfers to every future project.

Project management

Idea capture to autonomous execution

Set up and run multi-step work on the most optimal, research-backed conventions — with every piece of context it produces captured, organized, and kept as living reference.

  • Cheap idea capture — jot any initiative down for almost nothing; it's triaged, stored, and maintained, then promotable into a full plan on demand.
  • Research-backed plans — ideas become well-formed plans whose research, decisions, and materials are organized so you can thoughtfully one-shot the work.
  • Autonomous orchestration & scheduling — ready plans run through a propose-and-gate orchestrator and scheduled skill runs, with human gates on anything irreversible.
  • A project binder that compounds — Claude indexes every plan in a project and rolls its key materials into persistent context that grows on its own; the more you work in a directory, the better its output gets. Universal materials promote up for reuse anywhere.

Write-time governance

A doorman at every write

Every file and folder the assistant creates is checked the moment it's written, so your store stays discoverable and trustworthy without anyone remembering to be careful.

  • Allow · advise · deny — most policy teaches with a reminder; hard blocks are reserved for writes that would corrupt structure.
  • Conventions enforced at write time — frontmatter, naming, folder layout, and required indexes, applied by machinery rather than left to discipline.
  • Cross-document consistency — paired documents are flagged when one drifts out of sync with another.
  • Structural, not disciplinary — the check fires deterministically on every write it governs, regardless of whether the assistant remembers the rule.

Session management

Conscious, durable sessions

Claude keeps one long conversation alive, coordinates several at once, and cleans up after itself on the way out.

  • Autosave for your train of thought — checkpoints and a context-pressure ladder let a session survive its own memory being trimmed, or cold-start the next morning.
  • Multi-session coordination — concurrent windows track who's touching what and warn before two edit the same file.
  • Conscious hand-offs — Claude knows when to hand off to a fresh session, and reconciles what it changed before it does.
  • Decision quality — a consequential fork is held until the assistant has researched the options.

Automated capture

Outside information, brought in structured

Connectors and a single-writer pipeline turn the information you already deal with into reusable, structured assets — without re-pasting it into every session.

  • Deterministic by default — parse, transform, write once; repeated processing stays cheap and trustworthy, with an opt-in AI lane for genuine judgment calls.
  • One reconciler, many sources — emails, transcripts, calendar data, scrapes — all routed through a single governed writer that never collides with your edits.
  • Local and permanent — raw source, processed outputs, and a queryable record stay on your machine, so you're never taxed for changing your mind.

System personalization

Built to be bent to you

The whole foundation is made to be extended at designed seams — so you personalize it without forking it or losing your changes on an update.

  • A governed overlay — register your own file types, folders, tags, and writers on top of the sealed rulebook; your additions survive every upgrade.
  • The work-folder guidebook — a scaffolded home for any non-coding work, with flat and master layouts and worked examples.
  • The friction inversion — the most universal pieces are the most customizable, so you reshape exactly what's safe to reshape.

Obsidian is just the window

Brain Stem was designed with Obsidian in mind — but it does not depend on it. The whole "brain" is plain folders and Markdown files; any editor opens them, and the system runs exactly the same whether or not Obsidian is ever installed. Obsidian is simply the most convenient window onto what Claude produces session to session and project to project — not the engine underneath.

What Obsidian uniquely adds

The most visible Obsidian-specific affordance is the graph view — a visual of your knowledge graph, filtered by the tag taxonomy. The vault scaffold also seeds three starter Bases views and two .obsidian/ config files that only Obsidian reads. But the machinery runs on structured frontmatter — it reads the tags only to keep them healthy for that graph; tags and wiki-links are user-side navigation that degrade to plain text in any other reader, while every link the system writes for you — in the backlog, the indexes, the binder pages — is a plain relative Markdown link that resolves in any editor or viewer. Remove Obsidian and you lose the graph picture, the starter Bases views and those two .obsidian/ conveniences — the notes, the links and the shortcuts all still work. Even the Plans · Wiki · Projects · Work shortcuts are ordinary symlinks that resolve in any file browser.

Portable by design

Minimizing lock-in is a deliberate goal. Brain Stem leans almost entirely on a computer's native folders and files, universal Markdown, and a set of documented governing rules — so your knowledge never gets trapped in one app's format, and you can plug and play whatever tools you like around it. What it needs to run is short:

To run Brain Stem, all you needWhich means
A MacFor now — the scheduler and session-locking use macOS specifics; Linux and Windows aren't supported yet.
A terminalBuilt into macOS — nothing to install.
Local files & foldersAlready there; no database, no proprietary store.
A Claude Code accountFor now — native versions for other harnesses (e.g. Codex, Antigravity) aren't built yet.
The honest line: portable knowledge, a macOS runtime

Portability here is about your knowledge, not the engine. The running system — its background scheduler and the locking that keeps concurrent sessions from colliding — is built on macOS specifics (launchd and BSD lockf), and the project says so plainly: macOS only, today. The governing rules and the vault scaffold are ordinary bash and travel further in principle, but the shipped system targets a Mac. The distinction is the whole point — the brain it produces is plain text that goes anywhere, even while the engine that produces it still needs a Mac.

Multi-homing — the brain travels

Because the brain is nothing but plain text, it isn't locked to Claude Code. The folder Brain Stem builds can serve as a reference or resource for any other AI harness, in whole or in part — or you can point a local LLM at it and treat your accumulated knowledge graph as the feeder for a private, searchable knowledge base you query offline (grant any outside reader read-only access; the write-time governance lives in Claude Code). The value you build up stays yours, and stays portable across whatever systems you choose. How the conventions make that possible: Knowledge-graph extendability.
