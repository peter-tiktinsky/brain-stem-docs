Session management · close-out

Session Close

Every session leaves residue: records to settle, indexes that are now out of date, plans whose status moved, a project binder that no longer reflects what just happened. Brain Stem ships a session-close capability that handles all of that housekeeping for you, together with the brain-folder maintenance and governance audits that keep the knowledge layer well-structured over time. It runs automatically at the end of every session. You can also run it yourself, on demand, whenever you want the tidy-up now rather than at exit.

Fully autonomous by default. Regenerates what the machine owns, reports on what you own, never commits.

It runs on its own

When a session ends, Claude Code fires its session-end event and Brain Stem's three end-of-session hooks run in order:

  1. Deregister and launch the close. One hook marks your row in the session registry closed, spawns the registry reconciler in the background, and then spawns the librarian's session close itself — detached, so it can do real work without holding up the exit. The only thing that stops the launch is a close receipt less than a minute old, which is how a close you ran by hand just before exiting is not run twice.
  2. Write the episodic-memory row. A small, model-free hook records the session's anchor, touched files and next-session pointer; the close backfills its summary a moment later.
  3. Check whether memory consolidation is due. If at least a day and five sessions have passed since the last pass, a propose-only consolidation run is detached. It never deletes anything.
Graceful exit versus crash

Claude Code fires the session-end event on a graceful termination — ending the session from the prompt, clearing it, or logging out. A killed process, a crash, or a terminal that disappears may never fire it. Brain Stem covers that case with a backstop at the next session start: it scans the registry for a session that went stale without a clean close and runs the close for it, attributed to that session and its project directory, so the crashed session's own records are settled rather than whichever project you happen to open next.

What the close does

The close first auto-detects its scope from the registry. Alone, it runs everything. With peers still active, it runs everything except the shared registry sweep, which is deferred to whoever closes last. As the last one out, it runs the deferred sweep on everyone's behalf. Then it works through the chores below. They run in a fixed sequence, but the sequence matters only to the machine; what matters to you is what each chore does, why, and whether it writes or only reports.

The write-time hook only sees edits made through Claude Code's own file tools. These sweeps catch what arrived any other way (see what falls through the write), and every one of them reports rather than fixes, because a file you wrote is yours to change.

Periodic maintenance — on its own schedule

Some maintenance is worth running daily or weekly rather than at every close: folder-index sweeps, the library and rules indexes, memory hygiene, the tag and waiver audits. Brain Stem does not install a scheduler for them. Instead, each close checks when each sweep last ran and fires it only if its window has elapsed. A sweep never runs more than once per window, however many sessions you close inside it, and a window that elapses while you are away is caught at your next close.

Limits and caveats

  • "Advisory" means the chain never stops on a failure — it does not mean read-only. A chore that fails is logged and the next one runs. But the close does write: every machine-owned derived file above, and the plan-manifest stamps listed. What it never writes is prose you authored. Every write is either a whole derived file or a sentinel-bounded region, with everything outside the markers preserved byte-for-byte.
  • The dividing line is mechanical versus judgment. A fix runs unattended only when it is deterministic, loses no information, and is reversible or idempotent — regenerating an index from its source qualifies; rewriting a link across the corpus, backfilling fields on a note you wrote, or pruning a memory does not. Those are proposed, and you apply them (next section).
  • It never commits. No git write is reachable from any close path, automatic or manual, and a registry audit enforces that invariant on every capability that can commit. Backup is a separate, by-hand capability.
  • It exits cleanly, with one deliberate exception. A required capability that is present on disk but not executable is an install defect, and the close reports it with a non-zero exit instead of hiding it.
  • Every run leaves a receipt. One dated session-close log under the machine-local state directory, never in the vault: each chore marked ok, skip, dry-run, refused, stub or error, then a digest of the top finding categories with counts.

Running it yourself

/librarian session-close runs the identical chain. Two things differ. Its output reaches you in the session, so the chain results, any refusal and the receipt path are in front of you as they happen. And at the end it offers to run a backup if tracked targets have uncommitted changes — an explicit yes-or-no, never fired on its own. The automatic close, running detached, writes the same receipt and offers nothing.

After an automatic close, ask for the receipt

Findings from a detached close go to the receipt file. Two classes are re-surfaced at the next session start on their own: open placement findings at the plans root, and research declared against a plan that had already closed its scope. Everything else waits in the log. If you rely on the automatic close, start a session by asking Claude Code to read the latest session-close receipt and tell you what needs review — that is the one habit the automation does not replace.

About backup

/librarian backup is git-based: it commits your vault, install home, plans and work roots, excludes secret-bearing files and scans staged content for provider tokens before committing, then pushes to whatever remote you configured. A target with no remote still commits locally when you declare it local-only. You can run it any time, with or without a close; nothing in Brain Stem runs it for you. Keep at least one backup off the machine — a local commit does not survive a lost disk.

Beyond the close — acting on what it reports

Everything above is the close. What follows is its companion: the capabilities you invoke to act on what the close reported. Every entry is a librarian capability unless marked as a skill — invoke it as /librarian <name> with the flags shown; the prefix is left off below. Every one that writes defaults to a check or dry run; the flag is what turns it into a write.

How this ties back to memory and the binder

Close-out is where a session's contributions settle: episodic memory records what happened, the binder's generated pages and its situating card re-derive from the plans you touched, and the indexes refresh — so the next session in the project starts already oriented. The session keeps your place while you work (checkpoints) and coordinates with peers (the registry); close hands the durable residue back to context and memory.
